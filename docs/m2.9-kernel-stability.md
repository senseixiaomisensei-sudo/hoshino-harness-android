# m2.9 内核稳定性修复（fix/m2.9-kernel-stability）

## 现象（小米 15S Pro，m2.8.x）
- A：过程卡「已运行 0 步 · 0s · 已完成」+「请求未完成（TRANSPORT）：Connection error.」
- B：顶部「内核拒绝请求：session "<id>" is …」（Toast 截断）

## 根因
- B 文本来自 `SessionClient.rpcArgs` 把 dsh RemoteError 的 message 前缀「内核拒绝请求：」。在 prompt 路径上，dsh 0.2.2-alpha.2 能产生 `session "<id>" is …` 的是：
  - `dsh-session-persistence` `SessionAlreadyOwnedError`：`session "<id>" is already owned by an active write handle`。jsonl 持久化对 `session.lock` 取非阻塞 flock，持锁进程活着就拒绝。
  - `dsh-api-session-controller`：`is owned by subagent routing`（code `session/agent-busy`）/ `is a subagent session`。
  最符合「用一会儿后必现」的是第一种：内核被 HyperOS 杀/崩溃后，proot 下的 node 孤儿进程仍持有 session.lock（旧逻辑只按 runtime-process.json 记录的 pid 杀进程，且退出后不自动重启），新内核打开同一会话即被拒。
- A：`TRANSPORT / Connection error.` 是 dsh-llm 的“内核→服务商”传输错误码（plugins/hoshino-turn-policy/rules.ts、KernelNetwork 中国大陆 DNS 根因已由 #19 修复）。「0 步 0s」表示请求未到模型；崩溃/重启窗口里本地链路断开时也会落到同一卡片。

## 修复
- `KernelRecovery`（core-bridge）：错误分类（SessionOwned / SessionBusy / SessionNotFound / KernelLink / ProviderTransport / Other）、单次重试、busy 状态机（Cancel→Wait→Ready/GiveUp）、node 堆上限、崩溃原因提取、孤儿内核回收。
- `KernelLauncher`：启动前回收所有运行 node-host main.js 的孤儿进程（释放 flock）；node 加 `--max-old-space-size`=总内存 1/4，夹在 512–2048 MiB。
- `NativeKernel`：看门狗，内核意外退出后退避自动重启（1 分钟最多 3 次）。
- `SessionClient`：WebSocket 15s ping 心跳 + 指数退避重连（100ms→5s）。
- `DshHarnessClient.send`：会话被占/本地链路断 → 重启内核并重试一次，发 Notice「内核已重启，已自动恢复」；busy → 取消残留轮次并等待空闲；会话未打开 → session/list 重新加载后重试。恢复记录写 `filesDir/hoshino/kernel-audit.log`（脱敏，带崩溃原因行）。
- UI：内核/长错误改为对话框显示完整文本 + 「重试」。
