# m2.10 锁屏＝暂停，解锁自动继续（feat/m2.10-lock-gate）

对应差距报告 mika-delta-0.1.27 的 P2（Mika 0.1.27 · 736b53d），参照 Mika 0.1.28 的 `DeviceStateWatcher.kt`、`TaskGate.kt`、`KeepAwake.kt`。

## 之前

`phone_*` 遇到锁屏直接抛 `locked`（`PhoneController.steps()` / `read()` 的 find、collect），任务失败；悬浮胶囊自己听 SCREEN_ON/OFF，只在 USER_PRESENT 那一刻读一次 `isKeyguardLocked`，解锁时 USER_PRESENT 比锁屏界面退下早到，读到的还是「锁着」，之后没有广播 → 胶囊可能一直不回来。

## 现在

- `phone/DeviceState.kt`：全进程一份「主屏能不能操作」（熄屏或锁屏都算锁着）。广播只当「该重读」的信号；读到「亮着但锁着」且有人订阅时每 500 ms 再读，读到解锁或熄屏就停；熄屏不读，等 SCREEN_ON。任务门禁和胶囊都订阅它。
- `phone/LockGate.kt`：会改动后台屏的动作（`steps`、`find`、`collect`）在动手前过门禁：
  - 没锁：直接过；
  - 锁着：状态变成 `WaitingUnlock`，胶囊 / 前台通知 / 应用内虚拟屏页 / 聊天小窗显示「等待解锁」，解锁后自动继续；
  - 每个回调最多等 240 s（node fetch 的响应上限是 300 s），到点还锁着就回 `waiting_unlock` + `retry`，什么都没做；`android-phone` 插件自己再调一次（`withUnlockWait`），模型看不到中间态；
  - 一个会话累计等满 10 分钟仍锁着 → 如实失败（`code: locked`，说明这一步没做）；之后只要还锁着，再调立即失败，解锁后重新计时；
  - 胶囊 / 通知点「停止」，或内核中止这次工具调用（插件随即发 `stop`），等待立即结束，解锁后不会再执行这批旧动作；
  - 批内某一步前被锁：在本次回调剩余额度内等解锁再做；等不到就这一步不做、如实停下（`locked: ... NOT done`）；
  - 无审批档也不绕过：锁着的手机上什么都不做。
- `phone/KeepAwake.kt` + 设置「任务期间保持亮屏并调暗」（设置手机操作 → 保活与自愈，**默认开**，与 Mika 默认一致）：任务工作中（或步骤之间模型还在跑这一轮）持有 `SCREEN_DIM_WAKE_LOCK`，屏幕不自动熄灭但可以变暗；等你处理 / 等审批 / 接管 / 等解锁时再留 30 s 后释放；任务结束（后台屏释放）或关掉开关立即释放。不改系统设置和亮度，电源键照样能熄屏（随后门禁让任务等解锁）。和 Mika 的差别：Mika 用亮屏锁保持用户亮度，这里按任务要求用调暗锁。

## 验证

- JVM 单测：`app/src/test/java/app/hoshino/harness/phone/LockGateTest.kt`（LockState 解锁竞态、无订阅不读、胶囊订阅能看到解锁；门禁分段、总上限、停止、会话独立、批内额度；KeepAwake 持有/宽限/释放、需求判定；通知文案）。
- node 单测：`node-host/test/m210-lock-gate.test.mjs`（透明重调、只对 steps/find/collect、上限后如实返回、安全上限、中止时发 stop）。
- **未在真机验证**（需小米 15S Pro / HyperOS）：熄屏 30 s 后解锁能否 ≤1 s 自动续；解锁后胶囊是否回来；HyperOS 对前台服务持有 `SCREEN_DIM_WAKE_LOCK` 是否生效、是否真的变暗；锁屏时后台虚拟屏的读屏（observe 不过门禁）是否正常。
