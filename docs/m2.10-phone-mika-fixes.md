# m2.10 手机稳定性修复：移植 Mika v0.1.27 的 5 个修复

分支 `fix/m2.10-phone-mika-bugs`（基于 `integ/m2.10` = `43e7b42`）。来源：差距报告 `mika-delta-0.1.27` 的 P1、P3、P7、P8。Mika 是 Apache-2.0，出处见 `THIRD_PARTY_NOTICES.md`。

| # | 问题 | 改法 | 单测 |
|---|---|---|---|
| 1 | `Ed25519.kt` 用 `BigInteger.TWO`（API 33 才有）：Android 10–12（我们 minSdk 29）上一点「配对」类加载就抛 `NoSuchFieldError`，不在 `catch (Exception)` 里，整个进程崩、无障碍随之被系统停掉（Mika f28e8be） | 改成 `BigInteger.valueOf(2)`。并排查了其它 API 33+ 的 JDK 成员（`readNBytes`、`readAllBytes`、`transferTo`、`ByteArrayOutputStream.toString(Charset)`、`List.of`、`MutableList.removeFirst/removeLast` 等）：主源码里只有 `BigInteger.TWO` 这一处；`WebSearchProbe` 已用 `readNBytesCompat`，`AdbConnection.readText()` 用的是 Kotlin `ByteArray.toString(Charset)`，`removeFirst` 都在 `ArrayDeque` 上 | `MinSdkApiGuardTest`：扫 core-bridge 与 app 的 main 源码，列出的 API 一出现就失败（同一行写 `// minSdk-ok: 原因` 可豁免）；自带一份坏样例证明能抓到。JDK 17 上的单测本身测不出这类问题，所以用源码守卫兜底 |
| 2 | 防截屏窗口的截图错误码判断写成 `SDK_INT >= S`，这个错误码是 API 34 才有 | `ScreenshotErrors.isSecureWindow(sdk, code)`：`>= UPSIDE_DOWN_CAKE` | `ScreenshotErrorsTest`；守卫里也有一条：用到 `ERROR_TAKE_SCREENSHOT_SECURE_WINDOW` 的行必须判断 `UPSIDE_DOWN_CAKE` |
| 3 | shell 助手读剪贴板走 `ClipboardManager`：部分 ROM 上 `getPrimaryClip` 先读 `Settings.Global`，app_process 起的助手拿不到 ContentProvider，报 `calling package android does not match caller's uid 2000`，借剪贴板的中文输入失败（Mika e35865f / 7d2c48b） | 新 `ShellClipboard`：读内容 / 描述 / 有无直接调 `IClipboard`，按能力找签名（Android 14+ 四参 → 12–13 三参 → 已知 ROM 七参扩展），认不出（Android 10/11 两参）或拿不到服务时退回 `ClipboardManager`；比 Mika 多一步：直接调用抛错时也退回一次。写入、清空仍走 `ClipboardManager`（「不弹已复制浮层」标记仍生效）。借还逻辑 `ShellClip`/`ClipSwap` 不变 | `ShellClipboardCallsTest`（用 `Proxy` 按真实反射调用核对参数个数和类型）；`ShellClipTest` 不变 |
| 4 | `PairingCoordinator.begin()` 已在跑就直接 return：引导页开着超过 10 分钟后再点「开始配对 / 去无线调试」不重新计时，读不出配对码、不再弹填码通知（Mika dc7965b） | 新 `SlidingDeadline`：`begin()` 每次把 10 分钟从现在起重新算并重新找配对端口（`BuiltinShellEngine.startDiscovery()` 在找也重来）；`PhoneSetupScreen` 停在配对一步时**离开**引导页（ON_STOP）调 `begin()`，**回到**引导页（ON_START）且之前开始过配对时调 `resume()`；填码提交只续时、不重启找端口（免得丢掉刚找到的端口） | `SlidingDeadlineTest`（移植 Mika 4 例 + 多次续期 1 例）；`BuiltinShellEngineTest` 新增「还在找时再开始，从这时重新计时」与「找到端口」两例 |
| 5 | 无障碍事件流是每个服务实例私有的：服务被系统断开又重连后，任务里早先订阅的等待收不到新实例的事件，只能等超时、误判 `no_effect`（Mika a8c3aa6） | 事件流提到进程级 `A11yEventBus`（companion），只有当前连着的实例能发布，旧实例晚到的回调丢掉；`windowsOn` / 手势 / 截图都找当前实例；`AndroidPhoneScreen.awaitChange/watch` 直接订阅进程级流 | `A11yEventBusTest`：重连前订阅、重连后收到新实例事件；旧实例不能发布；多次重连不断流 |

## 验证情况

- 沙盒没有 JDK / Android SDK，本地没能编译和跑单测；编译与 JVM 单测靠 PR 上的 Verify CI（`:app:compileArm64DebugKotlin :app:testArm64DebugUnitTest :core-bridge:testDebugUnitTest :app:compileArm64DebugAndroidTestKotlin`）。
- 守卫的正则在合入前用等价的 Python 脚本对 main 源码跑过：改前恰好报出 `Ed25519.kt` 三处 `BigInteger.TWO` 和 `PhoneAccessibilityService.kt` 的错误码判断，改后为零。

## 没验证（需要真机）

- Android 10–12 真机 / 模拟器上点「配对」不再崩（只验证了源码里不再有 `BigInteger.TWO`）。
- 小米 15S Pro（HyperOS）等 ROM 上以 shell uid 读剪贴板、后台中文输入；Mika 的 `ShellClipboardDeviceTest` 真机测试没有移植。
- 引导页放 11 分钟后再点「开始配对」仍能读码、弹填码通知；已弹出的填码通知自带 10 分钟 `setTimeoutAfter`，续期后要等下一次状态变化或再次提醒才会重新弹出。
- 系统断开并重连无障碍后，正在跑的手机任务能继续收到事件。
- Shizuku 以 root 身份运行时 `IClipboard` 直接调用是否被拒（会退回 `ClipboardManager`，行为与以前一致）。
