# m2.10 · 插话撤回/编辑（T1）与断流重试补齐（T4）

对照：Mika 0.1.27 `9bd29de`（插话撤回/编辑）、0.1.24 `2d5ca72`（断流重试）。差距报告 §3 第 6、7 项。dsh 版本不变（0.2.2-alpha.2），未改 dsh 源码。

## T1 插话撤回 / 编辑

- 内核：dsh 原生 `session/updateQueue {sessionId, itemId, action:{kind:"remove"}}`（`dsh-api-session-controller` `updateQueue`）。inbox 的取走（claim）和移除都是一次 splice，内核串行执行；模型先取走则返回 `session/queue-item-not-found`。**撤回与取走只有一个成功**，不需要本地锁。
- `core-bridge` `SessionClient.rpcArgs`：内核拒绝时抛 `KernelRpcException(code, message)`（`IllegalStateException` 子类，消息不变），调用方可按 dsh 错误码判断。
- `HarnessClient.withdrawSteer(sessionId, itemId): SteerWithdrawal`（默认 `NotWithdrawable`）；`DshHarnessClient` 实现：先在 `SteerTracker.beginWithdraw` 记下意图（之后那条 `outcome=canceled` 的 splice 记为「已撤回」而不是「已停止」），并把 id 存进 `m1-session-metadata` 的 `withdrawn:<sessionId>`（重启/重放后状态一致），再发 RPC。`queue-item-not-found` → `AlreadyTaken`（提示「这句已经交给模型了，撤回不了」）。
- `SteerState.Withdrawn`；`InboxEffect.SteerWithdrawn` → `HarnessEvent.ItemDiscarded` 把气泡从 `SessionStore` 去掉（插话开启的那一组并回上一组，仍属同一轮）。
- 长按菜单（`Messages.kt`）：状态为「已收到，下一步处理」（`SteerState.withdrawable`）的插话多出「撤回」「编辑」。编辑 = 撤回成功后把原话放回输入框；输入框已有草稿、有待发附件、或原插话带附件时不提供「编辑」。
- 悬浮胶囊：当前胶囊（`PhoneCapsule`）不列出插话内容，没有需要隐藏的条目；读 `SessionStore` 的地方都看不到已撤回的气泡。
- 未做：排队中（`outbox` / `waiting:`）的消息本来就能在输入框上方的队列里移除，不在此改动；电脑端（dsh Web）追加的插话在手机上同样能撤（dsh 不区分来源），与 Mika「电脑插话手机不能撤」不同。

## T4 断流重试补齐

- 失败文案（`plugins/hoshino-turn-policy/rules.ts` `userReason('network')`）：不再写「检查 Base URL」。上游中途断开（`terminated` / `ECONNRESET` / `socket hang up` / `Stream ended without finish_reason` …，`isDisconnect`）如实说「连接在上游被断开」；连不上（DNS/拒绝/超时）说网络不通、查网络和代理。`core-bridge` `transportFailureHint(Reset)` 同样改为上游断开，不再建议改代理。
- 重试时清半句：dsh 把失败的流式尝试落成 `assistant/attempt`（不进上下文），RT16 重试开始新的尝试。`DshHarnessClient` 在 `assistant/attempt` 或「上一次尝试没落成 assistant/message 就开始了新尝试」时，用 `StreamRetry.discardedItems` 发 `ItemDiscarded` 去掉那次尝试已画出的正文、思考和托管搜索步骤。
- 「收到结束原因即算完整」：pi-ai 读 SSE 到 EOF；结束原因到了之后连接被重置时 undici 报 `terminated`，整段完整回答会被当成传输错误重来。新增 `plugins/android-api/stream-guard.ts`：最内层 fetch 包装，字节原样透传，看到结束原因（OpenAI `finish_reason`、Anthropic `stop_reason`/`message_stop`、Responses `response.completed`）后若读流失败就干净收尾（Anthropic 补一帧 `message_stop`）。结束原因之前的失败仍是失败。缺 `[DONE]` 但正常关闭的流 pi-ai 本来就算完成（测试锁定）。
- 模拟模型 `tools/mock-llm/context-loop.mjs` 新夹具：`cut-fixture`（前两次发半句就断）、`cutalways-fixture`（一直断）、`nodone-fixture`（有结束原因、无 `[DONE]`）、`finishreset-fixture`（结束原因后重置连接）、`slow-fixture`（两步慢工具，用来插话/撤回）。

## 验证

- `node-host/test/m210-steer-stream.test.mjs`（真 dsh 内核 + 模拟模型）：撤回 accepted、canceled splice、撤回的那句不进任何模型请求；已取走的再撤回得到 `session/queue-item-not-found`；断流两次后第三次完成、两次 `assistant/attempt` 带半句、半句不进 assistant/message 也不进重试请求；一直断 → 4 次请求后报错，文案含「上游」「断开」、不含「Base URL」；无 `[DONE]` 与结束原因后重置都算完成、只请求一次（去掉 stream-guard 时后者失败，已在本地确认）。
- `node-host/test/m210-stream-guard.test.mjs`：stream-guard 单测。`context-loop.test.mjs` 新增文案用例。
- Kotlin：`app/src/test/.../SteerWithdrawTest.kt`（`SteerTracker` 撤回/竞态/重放、编辑条件、`ItemDiscarded` 去半句与去气泡）、`core-bridge` `KernelNetworkTest.midReplyDropIsAnUpstreamDisconnect`。沙盒无 Android SDK，Kotlin 编译与单测由 CI（verify.yml）跑。
- 未验证：真机长按菜单的交互与动画、真实服务商的中途断流（只用模拟模型验证）、Anthropic/Responses 路线的 stream-guard 只有单测没有端到端。
